## Hello!

I'm a PhD candidate at NYU Tandon working on direct numerical simulation (DNS) of turbulence and combustion. Over the past several years I've run large simulations on ten supercomputers in the US, India, Norway and Saudi Arabia. I'm now building my own multi-GPU code aimed at 8192³ turbulence simulations. I'm at SC'26 to meet people working on GPU computing and large-scale scientific simulation. If we've just met, thanks for stopping by!

## HPC experience

### Applications

- **Decaying and forced turbulence in a periodic box:** pseudo-spectral DNS up to 4096³ grid points, run for about 200,000 eddy-turnover times. A dynamic regridding scheme I designed, which coarsens the grid as the flow scales grow, cut the computational cost by more than 5×.
- **Solver accuracy studies:** compared pseudo-spectral and finite-difference solvers for forced turbulence with GPU-accelerated Python (CuPy) codes.
- **Combustion:** detailed-chemistry DNS of high-pressure hydrogen/methane reheat flames with the massively parallel S3D solver.

## GPU code development

I'm developing my own multi-GPU pseudo-spectral DNS code for decaying homogeneous isotropic turbulence, with the goal of running 8192³ simulations. It solves the incompressible Navier–Stokes equations in a triply periodic box in double precision, with spherical dealiasing and an integrating-factor RK2 time stepper. I wrote it in C++17/CUDA, porting my validated single-GPU CUDA solver to multiple GPUs.

- **Allocation:** awarded a **750K-credit ACCESS Discover allocation** for this GPU code development.
- **Stack:** hand-written CUDA kernels, cuFFTMp for distributed 3-D FFTs, NVSHMEM for GPU-initiated communication, and GPU-aware MPI.
- **Design:** 1-D slab decomposition with one rank per GPU; all fields stay resident on the GPU.
- **Memory optimization:** reduced the field buffers from 20 to 14 (a ~30% smaller memory footprint), which also cut the time per step by 13%.

### Validation

I validated the port stage by stage against an independent NumPy/CuPy solver, matching it to machine precision (relative error ~10<sup>-16</sup>). The results are identical on 1, 2, 4 and 8 GPUs and on two different clusters, and the fields are bitwise identical across GPU counts and repeated runs.

- **Largest grid so far:** 1024³ on a single node of 4 A100s at 366 ms per step, using about 37 GB per GPU.
- **Efficiency:** profiling shows the pointwise kernels run at 83–88% of the GPU's peak memory bandwidth.
- **Why 2 GPUs scale poorly:** the global transposes go over a single NVLink pair, while 4 GPUs use three links in parallel.
- **Next:** scaling across nodes, on the way to 8192³ (see below).

### Scaling across nodes

Taking the code beyond one node exposed a problem in the network layer below NVSHMEM, not in the solver. On Delta's Slingshot-11 network, NVSHMEM traffic goes through libfabric's CXI provider. With libfabric's default memory-registration cache, the GPU-initiated transposes inside cuFFTMp hang at 512³ on two nodes. Turning the cache off restores correct, bitwise-reproducible results, but at a large cost, and 1024³ still hangs. The same code runs correctly across nodes on an InfiniBand cluster.

- **Diagnosis:** systematically tested libfabric memory-registration cache monitors and NVSHMEM heap settings, checking every workaround run against reference statistics.
- **Cost of the workaround:** with the cache off, 256³ on 8 A100s goes from 62.5 ms to about 1 s per step. At 512³, only ~21 ms of a ~2 s step is GPU compute.
- **Next step:** a portable backend that performs the distributed FFT over GPU-aware MPI (cuDecomp, or local cuFFT plus `MPI_Alltoall`), the vendor-supported path on Slingshot, while keeping cuFFTMp/NVSHMEM selectable on systems where it works well. I'm benchmarking GPU all-to-all performance across nodes first.
